# i18n — cycle de vie d'une langue (V2-21a)

Ce document décrit comment le produit gère ses langues : le **registre**, le
cycle de vie d'une langue, et le rituel d'ajout d'une langue future.

> **Principe directeur** — Le produit n'offre JAMAIS que les langues
> **publiées**. Aucune liste de langues codée en dur, nulle part (invariant 8
> étendu aux langues, cf. `CLAUDE.md` invariant 15). Une langue en brouillon ou
> en relecture est invisible pour tout utilisateur.

## Le registre : la table `languages`

Table introduite par la **migration 019** (seed dans `db/seed.sql`) :

| colonne | rôle |
|---|---|
| `code` | code ISO court (`fr`, `en`, `es`, `nl`, `de`, `it`, `sq`) — clé primaire |
| `name_native` | nom natif affiché dans le sélecteur (`Français`, `Nederlands`, `Shqip`…) |
| `status` | `draft` \| `in_review` \| `published` — **le seul** qui décide de la visibilité |
| `sort_order` | ordre d'affichage (10, 20, 30…) |
| `register_note` | consigne de **registre** (vouvoiement/tutoiement…) imposée au modèle à la génération |

Le registre est **la source unique** des langues offertes. Le lisent :

- **Backend** : `repo.published_languages(conn)` / `repo.published_language_codes(conn)`.
- **Enrich / CLI** : `db.published_language_codes(conn)` (repli des cibles de traduction).
- **SSR du guide** : lecture directe de la base (`api/routers/guide.py` charge la
  carte code→nom natif et la passe à `guide_page.render_guide`).
- **Front** : `GET /languages` (endpoint public) via `frontend/js/languages.js`
  (`publishedLanguages()` / `publishedLanguageCodes()`), consommé par le menu de
  partage et la modale « langue du locataire ».

Le `properties.published_langs` d'un logement (langues traduites pour CE guide)
est **croisé** avec le registre à la lecture : une langue dépubliée globalement
disparaît du guide même si elle reste dans `published_langs`.

## Cycle de vie d'une langue

```
draft  ──(génération + relecture)──▶  in_review  ──(corrections importées)──▶  published
  ▲                                                                                │
  └───────────────────── (dépublication à chaud, non destructive) ────────────────┘
```

- **`draft`** — la langue existe au registre, ses libellés peuvent être générés,
  mais **rien n'est offert** à l'utilisateur.
- **`in_review`** — export envoyé à un relecteur (toujours invisible).
- **`published`** — la langue apparaît partout (sélecteurs, partage, détection).

Le passage d'un état à l'autre est un simple `UPDATE languages SET status=…` :
c'est une **opération**, pas un développement, et elle prend effet **sans
redéploiement**. Le **seed ne touche jamais `status`** (un rejeu ne dépublie ni
ne republie une langue).

État actuel (V2-21a) : `fr`/`en`/`es` = `published` ; `nl`/`de`/`it`/`sq` =
`draft` (générés puis relus, publiés une à une en missions V2-21b…n).

## Registre de langue (`register_note`)

La décision de registre est tranchée **une fois par langue** et imposée au
modèle à chaque génération (la cohérence prime sur la qualité ponctuelle). Défauts
alignés sur le ton du guide FR (vouvoiement) :

| langue | registre |
|---|---|
| de | vouvoiement (Sie) |
| nl | vouvoiement (u) |
| it | voi (le guide s'adresse au groupe de voyageurs) |
| sq | forme de politesse (ju) |

Ajustable en base (`UPDATE languages SET register_note=… WHERE code=…`), jamais
en dur dans le code.

## Ajouter une langue future (PT, CA…)

1. Insérer la ligne au registre en `draft` (`INSERT INTO languages …`) avec son
   `name_native`, un `sort_order` et sa `register_note`.
2. Générer l'inventaire des libellés (outillage volet 2/3 de V2-21a).
3. Faire relire (export CSV → correction → réimport).
4. Publier : `UPDATE languages SET status='published' WHERE code='pt';` — la
   langue apparaît immédiatement partout.

Rien à redéployer, aucune liste de langues à modifier dans le code.

## Vérification (garde-fou i18n)

Aucune liste de langues ne doit **décider de ce qui est offert** hors du
registre. Les seuls résidus admis sont des **libellés d'affichage** (avec repli
sur le code brut) :

```bash
grep -rnE "'(en|es|de|nl|it|sq)'" backend/api frontend/js
```

Le test clé (`tests/test_api.py::test_unpublishing_a_language_removes_it_everywhere`)
vérifie qu'une langue passée en `draft` disparaît de l'endpoint, du sélecteur du
guide et de `/g/{token}/data`.

## Libellés statiques : inventaire + relecture (volet 2)

Les **libellés statiques** du guide voyageur (interface, noms de chapitres, de
sections, de catégories de POI, cuisines) sont traduits hors du pipeline de
contenu (M-09, qui traduit le contenu propriétaire par logement). Trois outils,
tous idempotents et rejouables :

### 1. Inventaire — `ops/i18n_inventory.py`

**Généré par script** depuis les sources vivantes (le code `api.guide_page` +
le seed en base), **jamais maintenu à la main**. Écrit `i18n/inventory.json` :
pour chaque libellé, une **clé stable** (`ui.eyebrow`, `chapter.A`,
`section.A_arrival.name`, `poi_category.hospital`, `cuisine.italian`…), un
contexte FR (aide au relecteur) et les textes source **FR/EN/ES** existants.

Les clés sont construites par les helpers de `api/i18n.py` (`ui_key`,
`section_name_key`…) et utilisées **aux deux bouts** : par le collecteur ET par
le rendu SSR (l'overlay est interrogé avec ces mêmes clés) → aucune dérive
possible entre « ce qu'on traduit » et « ce qu'on affiche ».

```bash
python ops/i18n_inventory.py            # (re)génère i18n/inventory.json
python ops/i18n_inventory.py --check    # échoue si l'inventaire a changé (gate CI)
```

Le mode `--check` est l'**outil de non-régression i18n** : une clé ajoutée au
code/seed (nouveau libellé) ou retirée fait échouer la CI tant que
`i18n/inventory.json` n'est pas régénéré et committé.

### 2. Export relecteur — `ops/i18n_export.py --lang de`

Produit `i18n/review/ui_<lang>.csv` (UTF-8 avec BOM → Excel/Numbers), colonnes :
`cle, contexte, source_fr, proposition, correction`. Le relecteur ne remplit que
la colonne **`correction`** (vide au départ). `proposition` = la traduction déjà
en base (vide tant que rien n'a été généré/importé — volet 3 la remplit).

### 3. Réimport — `ops/i18n_import.py i18n/review/ui_de.csv`

Écrit les libellés traduits en base. Pour chaque ligne :
`texte_final = correction (si remplie) sinon proposition`. **Idempotent** (upsert),
**refuse les clés inconnues** (absentes de l'inventaire) avec un rapport clair,
**ignore** les lignes sans texte final. La langue est déduite du nom de fichier
(`ui_<lang>.csv`) ou forcée par `--lang` ; elle doit exister au registre.

### Où vivent les traductions statiques

Une **seule** source de vérité : la table **`ui_translations (lang, key, text)`**
(migration 020). Elle ne porte **que** les langues supplémentaires
(nl/de/it/sq…) : les libellés **FR/EN/ES restent portés par le code**
(`guide_page._UI`…) et le **seed** (`name_i18n`). Au rendu, le SSR **superpose**
`ui_translations` de la langue effective par-dessus le code (helper `_seed_label`
/ `_t` / `_cuisine_label`, overlay dans un `ContextVar`). Pour FR/EN/ES l'overlay
est vide → **rendu strictement identique** (non-régression du volet). Une clé non
traduite retombe sur le FR (repli élégant, jamais de trou).

### Rituel d'ajout d'une langue (rappel, complété)

1. Registre : `INSERT INTO languages … status='draft'`.
2. `ops/i18n_inventory.py` (à jour) → `ops/i18n_export.py --lang xx`.
3. Génération des propositions (volet 3) puis relecture (colonne `correction`).
4. `ops/i18n_import.py ui_xx.csv` → `ui_translations` peuplée.
5. `UPDATE languages SET status='published' WHERE code='xx';` → livrée partout.

## Hors périmètre (à ce stade)

- **Génération des 4 langues brouillon** (propositions Claude) : volet 3.
- **Libellés restés FR délibérément** : le **cahier d'équipe `/s/`** (M-13, French
  by design), le **back-office propriétaire** (SPA française), les **emails
  transactionnels** (`api/emails.py`, destinataire = le propriétaire, français).
  Ces surfaces ne sont pas multilingues → hors inventaire tant qu'on ne décide pas
  de les localiser. Les **libellés de champ** du seed (`field_schema.*.label`)
  suivraient le même patron que `section.*.name` s'il fallait les traduire (non
  requis aujourd'hui : ils retombent sur le FR dans un guide publié en langue
  supplémentaire).
- **Poster PDF** (`api/poster.py`, M-26) : reste FR/EN/ES tant que son inventaire
  de libellés n'est pas traduit — non piloté par le registre (une langue publiée
  sans texte de poster créerait un artefact vide).
- **`/g/{token}/data`** : renvoie les `name_i18n` bruts du seed (FR/EN/ES) ; il
  n'applique pas l'overlay `ui_translations` (surface API secondaire — le produit
  livré est le SSR). À enrichir si un consommateur tiers le demande.
- Contenu des guides (sections remplies, POI) : déjà couvert par le pipeline de
  traduction par logement (M-09).
